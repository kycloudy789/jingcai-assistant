## D1 采用"零运行时依赖 + 纯 ES6 JS"，不引入 TypeScript 构建链

- 日期：2026-11-04
- 状态：已采纳
- 背景：主方案推荐 TypeScript（或项目现有标准）；实测本机 `registry.npmjs.org` 与 `registry.npmmirror.com` 均不可达（HTTP 000），`tsc`、`jest` 均无法安装。
- 决策：小程序端使用原生 JS + WXSS，云函数使用 Node CommonJS JS；类型信息通过 JSDoc 注释表达；测试使用 Node 22 内置 `node:test`。
- 替代方案与否决原因：
  - 引入 TypeScript/tsc：无法安装依赖，安装后也无法保证 CI 可复现。
  - 自建 esbuild 产物：同样需要下载二进制，网络不可用。
- 影响：无编译步骤，改源码即生效；类型安全性弱于 TS，用"运行时校验 + JSDoc + 单测"补偿。**号码与奖级的关键正确性必须靠校验函数与测试保证，而不是类型。**
- 复检条件：npm 网络恢复，或项目迁入有内网镜像的 CI 环境。

## D2 `shared/` 为唯一源，通过脚本同步到小程序与云函数目录

- 日期：2026-11-04
- 状态：已采纳
- 背景：判奖规则、号码校验必须"前后端同一份实现"，否则出现前端判一级、后端判二级的偏差；但小程序 `require` 不能跨出 `miniprogramRoot`，云函数也只能打包自身目录。
- 决策：`shared/` 为唯一源；`scripts/sync-shared.js` 将其复制到 `miniprogram/shared/` 与每个 `cloudfunctions/<fn>/shared/`。复制产物一并提交，保证开发者工具直接可运行。
- 影响：修改 `shared/` 后必须执行 `npm run sync:shared`；测试中会校验"复制产物与源文件哈希一致"，防止忘记同步。
- 复检条件：若将来接入支持 monorepo 打包的构建链，可改为构建期内联。

## D3 开奖数据源：官方网页解析为主，CSV/JSON 手动导入为强制兜底

- 日期：2026-11-04
- 状态：已采纳（列表页可达性已实测；详情页与云函数出网待阶段 2 验证）
- 背景：主方案要求先核实官方是否存在可合法稳定使用的接口；本轮实测中国福彩网"往期开奖公告"页为服务端渲染 HTML，含期号、开奖日期、开奖号码、一二等奖注数与金额、销售额、奖池、公告详情链接。
- 决策：
  1. 适配器按 `source` 抽象，首版实现 `cwl_web_list`（列表页 HTML 解析），字段映射见 `data-source-plan.md`。

## D4 规则版本按"期号"而非"日期"选择

- 影响：旧期若未建档权威规则，明确提示"不支持自动核对"，而不是用新规则静默算错。

## D11 福运奖空字段默认判为 `unknown`，不猜测

- 日期：2026-11-05
- 状态：已采纳
- 背景：官方接口对双色球提供 `fyjCount` / `fyjMoney`。实测 2026 年数据该字段为空。但"空"既可能是"未执行特别规定"，也可能是"公告延迟/字段未提供"；且奖池曾达 15 亿回落到 10 亿时特别规定**仍在执行**，仅凭奖池金额反推会出错。
- 决策：`fyjMoney > 0` → `active`；期号 < 2026014 → `not_applicable`；其余 → `unknown`。提供配置 `app_config.fuyunEmptyMeansInactive`（默认 `false`），由用户在核对连续若干期官方公告后自行打开，打开后空字段判为 `inactive`。
- 影响：默认配置下，"恰好命中 3 红"的票据不自动判奖，转人工复核。这是**有意选择**：少判一次错奖，比多判一次错奖代价小。

## D14 写操作合并为 `ticketService` 单函数，而非按动作拆 5 个云函数

- 日期：2026-11-05
- 状态：已采纳
- 背景：主方案 12.1 按动作列出 `saveTicket` / `confirmTicket` 等函数。单人应用若照搬，会产生 5 份几乎相同的鉴权外壳、5 次部署、5 个冷启动实例。
- 决策：写入侧合并为 `ticketService`（`action ∈ create|update|confirm|void|delete`），读取侧为 `queryTickets`（`mode ∈ list|detail|summary`）。动作名、参数、错误码与主方案一致，行为不变。
- 影响：部署清单从 7 个减少到 2 个（连同阶段 2 的 4 个共 6 个）。**代价**：单函数代码更长，需靠 `shared/domain/tickets.js` 保持判定逻辑独立可测。
- 复检条件：若接入多人使用或需要按函数级别做权限/配额控制，应按动作拆分。

## D15 实际金额必须由用户录入，系统只给"已验证的"建议值

- 日期：2026-11-05
- 状态：已采纳
- 背景：主方案 6.4 要求"不默认推断用户买了几注，实际金额由用户录入，或在规则明确时由默认值辅助填充"。
- 决策：
  1. 草稿阶段 `actualCost` 一律 `null`；确认购买时必须显式给金额（允许 0，代表赠票），否则拒绝。

- 影响：统计里的金额始终是"用户声称的支付额"，不掺入系统推断；代价是录入时多填一个数字。

## D16 判奖结果独立存储，`checkSummary` 只是展示缓存

- 日期：2026-11-05
- 状态：已采纳
- 背景：列表页要显示"中奖/未中奖"徽标，但主方案要求核对结果存 `ticket_checks`，且 `checked` 是派生态、不写回 `purchaseStatus`。
- 决策：
  1. 判定结果全部写 `ticket_checks`（含 `ruleVersion` / `drawHash` / `hitDetails` / `pendingReason`），作为唯一事实来源。
  2. `ticket_records.checkSummary` 只存展示摘要（状态、奖级、金额、命中号码），由 `checkTickets` 每次重算覆盖，**任何代码不得读取它做判定**。
  3. `purchaseStatus` 永不因核对而改变。
- 影响：列表无需 N+1 查询核对表；代价是一处冗余，靠"只写不读"的注释与约定约束。

## D17 只有"需要人看"的待核验才落库，未开奖不写记录

- 日期：2026-11-05
- 状态：已采纳
- 背景：若把 `NO_DRAW` / `DRAW_NOT_VERIFIED` 也写成待核验记录，每张未开奖的票都会产生一条"待人工核验"，把真正需要关注的情形淹没。

- 影响：前端"一键核对"在 `skipped == total` 时提示"数据尚未同步/核验"，而不是抛出一堆待核验。

## D18 AI 工具只读 + 身份由服务端注入，模型无权指定用户

- 日期：2026-11-05
- 状态：已采纳
- 背景：主方案 13.3 明确禁止模型获得通用查询/写库能力。
- 决策：
  1. 只注册 7 个只读工具（查开奖、查本人号码、查统计、查核对、查规则），不提供任何写操作。
  2. `ownerOpenId` 由云函数从运行上下文注入执行器，工具参数里没有"用户"这一项；模型即使伪造 `userId` 也会被 schema 丢弃。
  3. 工具参数白名单校验（彩种枚举、期号 7 位、limit 上限 20、窗口 30/50/100），越界直接拒绝，不"理解着执行"。
  4. 结果里找不到数据时返回 `ok:false` + 原因，让模型如实说"没有"，而不是让它自由发挥。
- 影响：AI 的能力边界 = 这 7 个查询；扩展能力必须显式加工具并补测试。

## D19 对话成本与失控防护：3 轮 / 单轮 4 个 / 总量 8 个 / 900 tokens

- 日期：2026-11-05
- 状态：已采纳
- 背景：模型可能反复调工具，成本不可控；单人使用也不该出现一问答几十次调用。
- 决策：`runToolLoop` 硬性限制轮次与工具次数，超限后**不带工具**再请求一次做总结（避免空回复）；单次响应 25s 超时；输出上限 900 tokens；输入上限 1000 字；会话只带最近 10 条历史。
- 影响：极端情况下会牺牲一点完整性（模型只能说"数据不足"），换取可预期的成本与延迟。

## D20 主线改为纯静态站（GitHub Pages），放弃小程序作为交付形态

- 日期：2026-11-05
- 状态：已采纳（用户决策）
- 背景：用户决定不再走微信小程序，改用 GitHub 免费托管。小程序版需要云开发环境、云函数部署、平台审核，链路过长。
- 关键约束：官方开奖接口**没有 CORS 头**（实测），浏览器无法直连；静态站也不能安全保存 API Key。
- 决策：
  1. 交由 **GitHub Actions 定时抓取**官方数据，产出 `web/data/draws/*.json` 提交到仓库；页面同源读取，天然无跨域。
  2. 个人数据（号码、核对结果）存**本机 IndexedDB**，IndexedDB 不可用时降级 localStorage；提供导出/恢复。
  3. 判奖、校验、状态机**不重写**，继续复用 `shared/` 纯函数，通过零依赖打包脚本内联进 `web/dist/app.js`。
  4. Web 版**不提供 AI 助手**（无安全密钥存放位置）与候选号码生成（合规风险 + 无服务端闸门）。
  5. 小程序版代码保留在 `miniprogram/`、`cloudfunctions/`，不再作为主线维护。
- 影响：单机数据没有跨设备同步；开奖数据最多滞后一个定时周期（每天 2 次，可手动触发）。
- 复检条件：需要多设备同步或 AI 能力时，需重新引入后端（Cloudflare Workers 等）。

## D21 静态站保留 AI：用户自带 Key、只存本机、直连 DeepSeek

- 日期：2026-11-05
- 状态：已采纳（用户要求"功能不缩减"）
- 背景：原计划在云函数里放 `DEEPSEEK_API_KEY`；改成静态站后没有服务端，Key 无处安全存放。
- 实测：`api.deepseek.com` 对 `Origin` 回显 `Access-Control-Allow-Origin`，浏览器可直连（不需要代理）。
- 决策：
  1. Key 由用户在「AI」页自己粘贴，存 `localStorage`；界面明确告知"同浏览器脚本/扩展理论上可读"并提供「清除密钥」。
  2. 请求从浏览器直发 DeepSeek，不经过任何第三方；费用由用户自己的账户承担。
  3. 工具仍是 7 个只读查询，复用 `shared/ai/tools.js` + `shared/cloud/aiTools.js`（通过 `web/js/localdb.js` 适配本地存储），判奖/校验逻辑零复制。
  4. 轮次与 token 上限不变（3 轮 / 单轮 4 个 / 总量 8 个 / 900 tokens / 输入 1000 字）。
- 影响：这是"能用"与"绝对安全"之间的取舍——Key 暴露面从"服务端环境变量"变成"本机浏览器"。若将来需要多人使用，必须改回服务端代理。
- 复检条件：出现跨设备共享需求，或用户不愿自备 Key。

## D22 注数与倍数分离：随机生成 N 注不同号码

- 日期：2026-11-05
- 状态：已采纳（用户反馈）
- 背景：原先"随机一注 + 倍数"容易被理解成"同一注打多倍"，但用户想要的是 2–3 注不同号码。
- 决策：
  1. 表单新增「注数」（1–5），随机按钮按注数生成**互不相同**的组合（按号码串去重）。
  2. 「倍数」仍表示每注打几倍，两者独立：金额建议 = 注数 × 倍数 × 单价。
  3. 每注独立成一条 `draft` 记录（不是一条记录存多注），便于逐注确认购买、逐注作废。
  4. 多注时用标签切换编辑目标，任选一注都可单独改号/删注。
- 影响：一次保存会产生多条草稿；统计按"注"计，与线下小票一行一注的口径一致。

## D23 静态站的候选闸门：保留开关，新增"本人知情确认"状态

- 日期：2026-11-05
- 状态：已采纳

- 决策：

  2. 新增 `self_attested_personal_use` 状态，**只有调用方显式传 `acceptSelfAttested: true` 才认**。Web 端传，云函数不传。
  3. Web 端必须由用户勾选并点「我已了解，开启」才写入该状态，关闭时重置回 `not_checked`。

## D24 候选生成确定性化，且刻意不读历史频次

- 日期：2026-11-05
- 状态：已采纳
- 背景：需求给了 random/balanced/preference 三个策略名，未给定义；也未说明是否要"分析往期选号"。
- 决策：
  1. 随机源用 mulberry32 + FNV-1a 种子哈希，同参数同种子必得同结果，并回传实际种子，保证可复盘。
  2. `balanced` 只做结构均衡（分区 + 奇偶），**不读开奖频次**。
  3. `preference` 定义为"必含/排除号码 + 随机补足"，不做偏好学习。
  4. 历史频次以 `get_number_stats` 单独提供，只作描述性统计，并强制附带样本量与"不代表未来倾向"。
- 理由：用历史频次加权会让输出显得"有依据"，但双色球每期独立，冷热对下期没有信息量。把随机包装成推断，是本项目明确拒绝的做法（与提示词规则一致）。
- 影响：生成的号码在统计上就是随机的，这是特性不是缺陷；想"更均衡"用 balanced，想"指定号码"用 preference。
- 复检条件：若将来引入真正的概率模型（并愿意为其结论负责），必须单独评审，不能藏在候选生成里。

## D25 "分析选号"= 拥挤度优化，不是预测

- 日期：2026-11-05
- 状态：已采纳（用户要求"要跟机选有区别"）
- 背景：用户认为纯随机与机选无差别，要求 AI 分析选号。此前拒绝过"用历史频次加权"，因为没有预测力。
- 调研结论：唯一有真实期望值影响的是**浮动奖的均分**——双色球一/二等奖、快乐8选十中十按中奖注数平分；避开大众偏好（生日号、连号、等差、上期重号）可降低被平分的概率。依据 Cook & Clotfelter (1993)、Farrell 等 (2000)、Cox 等 (1998)、Baker & McHale (2009)。
- 决策：
  1. 新增 `shared/domain/analysis.js`：结构画像 + 拥挤度指数（`crowd@1.0.0`）。
  2. 新增策略 `analyzed`：结构硬约束 + 拥挤度最低 + 和值偏离惩罚。
  3. 目标函数 = `拥挤度 + |和值 − 中心| × 0.25`，即"两者兼顾"；批次里同时给出代价摘要（平均拥挤、和值范围、几注含大号/连号）。
  4. 拥挤度是**推定值**（福彩不公布投注分布），界面必须标明，不得表述为实测人数。
  5. 仍然不做"按频次加权"；冷号只作为"大众少选"的代理，不表述为"该回补"。
- 影响：号码会比随机更"不规整"（可能 32/33 同出、带连号），这是特性，UI 如实展示代价。
- 复检条件：若拿到真实的号码投注分布，应替换权重并从研究发现降级为实测模型。

## D26 恢复备份改为"先预览、合并覆盖、不删除"

- 日期：2026-11-06
- 状态：已采纳
- 背景：原实现选完文件直接写库，用户不知道会被覆盖什么；恢复是最容易造成数据损失的操作。
- 决策：
  1. `previewImport()` 只读计算：每类数据给出「新增 / 覆盖 / 保留现有」三个数，以及备份导出时间。
  2. 必须点「确认恢复」才调用 `importAll()`；取消不写任何字节。
  3. 恢复语义是**合并覆盖**：同 id 覆盖，备份里没有的现有记录保留（绝不静默删除）。
  4. 若备份里 `gate.candidateGenerationEnabled === true`，预览必须显式提示"会一并开启闸门"。
  5. 清空拆成分类操作，`clearCollection()` 白名单只允许 tickets/checks/candidates；draws 与 meta 不允许清空。
- 影响：恢复不会"回滚到某个时间点"，只会在现有数据上合并。想要完全回滚，需先清空再恢复。
- 复检条件：若将来支持多份快照/版本历史，应提供"替换式恢复"作为显式选项，而不是改默认行为。

## D27 每日自动更新走本机计划任务，而不是 GitHub Actions

- 日期：2026-11-08
- 状态：已采纳
- 背景：GitHub 托管 Runner 抓福彩网被 WAF 按 IP 拦（403，实测），Actions 定时抓取不可用；数据因此只能靠人工跑，导致落后 2 期。
- 决策：
  1. 用 Windows 计划任务每天 21:35 与 22:20 各跑一次 `publish-data.js`（双色球 21:15、快乐8 21:30 开奖，留出公告延迟）。
  2. `publish-data` 增加**变更检测**：先比对远端 blob sha，数据没变就不提交，避免每天产生空 commit。
  3. 计划任务只在本机、登录状态下运行；卸载用 `npm run task:remove`。
  4. 同时补历史：双色球用 pageNo 翻页、快乐8 用 issue 区间，`npm run sync:history` 各 300 期。
- 影响：自动更新依赖这台电脑开机且已登录；关机当天需手动跑一次。
- 复检条件：若将来有国内可用的托管 Runner（或官方接口放开海外 IP），应迁回纯云端。
