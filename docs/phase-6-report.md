## 2. 三策略的实际含义

原方案只给了策略名，没给定义。这里的定义是我做的取舍，写清楚以免后续误解：

| 策略 | 做法 | 明确不做什么 |
|---|---|---|
| `random` | 号码池等概率抽取 | — |
| `balanced` | 采样 48/64 次，取"三区偏差 + 奇偶偏差"最小的一组（双色球 2/2/2、奇偶 3:3；快乐8 四区 3/3/2/2、奇偶 5:5） | **不读历史频次**，不按冷热加权 |
| `preference` | 必含号码必出现、排除号码必不出现，其余随机补足 | 不做"根据你的历史偏好学习" |

`balanced` 用"多次采样取最优"而不是构造式算法：构造式在"奇偶与分区约束冲突"时会生成失败，采样法永远不会产出非法组合，并且因为随机源确定，同样完全可复现。

**为什么不做"按历史频次加权"**：那是把"冷号该回补/热号会延续"包装成算法能力。双色球每期独立，频次对下一期没有任何信息量；写进代码只会让输出看起来更"有依据"。所以候选生成**不读开奖数据**，历史统计只作为描述性信息单独展示（`get_number_stats`）。

## 3. 确定性：可复现是这轮的核心设计

同一个 `(game, strategy, count, seed, params)` → 永远同一批号码。

- 随机源是 mulberry32 + FNV-1a 哈希，不是 `Math.random()` 直出。
- 不传种子时自动生成，并把实际种子回填到表单，用户下次能复现同一批。
- 批次里存 `parameterSnapshot`，用它可以完全重放：用例「参数快照完整记录，可据此复现」直接做了这件事。

这一条的实际用途是**复盘**：开奖后你能确认"当时这批是怎么来的"，而不是面对一堆号码说不清。

## 4. 闸门设计（与小程序版的差异）

小程序版的闸门是：`wxComplianceStatus === 'approved' && candidateGenerationEnabled`。
静态站没有平台可审批，照抄这套会让功能永久不可用。

本轮做法（决策 D23）：

```
默认（未核实）           → 关闭
pending / rejected      → 关闭
approved（平台批准）     → 按开关
self_attested_personal_use（本人知情确认）→ 仅当调用方显式 acceptSelfAttested 时才认
```

- Web 端传 `acceptSelfAttested: true`，用户必须在选号页勾选并点「我已了解，开启」。
- 云函数**不传**该参数，行为与之前完全一致（有用例锁死：`未传 acceptSelfAttested 必须拒绝`）。
- 关闭后：不能生成、不能导入；**已生成的批次与草稿保留**（不删用户数据）。

## 5. 数据与不变量

### 5.1 批次记录（`candidate_batches`，浏览器本地）

```jsonc
{
  "id": "b_...",
  "ownerOpenId": "local",
  "game": "ssq",
  "strategy": "balanced",
  "count": 3,
  "targetIssue": "2026127",
  "algorithmVersion": "candidate@1.0.0",
  "randomSeed": 3472741477,
  "seedGenerated": false,
  "parameterSnapshot": { "include": [], "exclude": [], "blueFixed": null },
  "complianceState": "self_attested_personal_use",
  "createdAt": "2026-11-05T…",
  "groups": [{ "index": 0, "numbers": { "red": [...], "blue": 7, "kl8": [] }, "key": "...", "displayText": "..." }],
  "importedAt": null,
  "importedTicketIds": []
}
```

### 5.2 三条不变量

1. **候选 ≠ 已购买**：导入只会生成 `purchaseStatus: 'draft'`，`actualCost` / `purchaseAt` 恒为 `null`。
2. **一注一条记录**：3 注批次导入 = 3 条草稿，便于逐注确认、逐注作废（与线下小票一致）。
3. **整体成功或整体失败**：任一组号码或期号不合法 → 一条都不写，避免"部分导入"的糊涂账。

## 6. 没实现 / 与需求文档不一致的地方（重点）

这一节是这份报告最该看的部分。

### 6.1 "服务端每次校验" —— 静态站无法按原样实现

- 需求写的是"服务端每次都校验 `candidateGenerationEnabled && wxComplianceStatus === 'approved'`"。
- 现状：没有服务端。闸门状态存在浏览器里，每次生成/导入/调用 AI 工具前都会读一遍并校验。
- 差别在哪：**这不是不可绕过的强制**。懂技术的人可以直接改 localStorage 或改前端 JS 绕过。
- 为什么还能接受：这是单人自用工具，绕过闸门等于骗自己；闸门的作用是防止"我不知不觉在用被限制的功能"，不是防别人。
- 若要真正服务端强制，需要引入后端（Cloudflare Workers 或回小程序云函数）。已记入 D23 复检条件。

### 6.2 "关闭时前端入口隐藏" —— 我改成了"入口可见但不可用"

- 原因：静态站里如果把入口藏起来，用户没有任何地方可以把它打开，功能等于永久消失。
- 现状：`选号` 页签始终存在；关闭时只显示一张说明卡和「我已了解，开启」按钮。
- 安全性没有降级：生成/导入/AI 工具仍然全部拒绝，按钮藏不藏不影响闸门。

### 6.4 一个需要你知道的副作用

备份文件现在是 `jingcai-web@2`，包含 `candidates` 与 `meta`。而 `meta` 里有闸门状态，
所以**从"已开启"的备份恢复到另一台设备，会连带把闸门打开**。这符合"备份=完整还原"的预期，
但如果你打算把备份发给别人，需要知道这一点。旧版 `@1` 备份仍可导入（用例已覆盖）。

## 8. 已知限制

- 页面渲染只在无头 Edge 验证过，未做真机触控验证（选号网格在窄屏的横滑体验需人工看）。
- 批次数量没有上限，长期使用后列表会变长（本地存储容量通常够，但没有做分页）。
- `balanced` 是"采样取最优"，不是数学意义上的均匀分布；它的价值是结构不极端，不是概率更优。
